Case Study — Star Sports × Cricinfo

Stats Dashboard: One Source, Every Format

Star Sports was paying an outside vendor for cricket stats it already owned through Cricinfo. Stats Dashboard was built to close that gap — one tool to browse, generate, and publish stat modules straight to broadcast, apps, and social, without the licensing cost.

The problem

Paying twice for data already in-house

Business problem

Star Sports paid an external API vendor for cricket stats, adding recurring licensing cost for data that Cricinfo, a sibling property, already had.

Root cause

There was no bridge between Cricinfo's data and Star Sports' publishing needs — no tool let a user browse Cricinfo modules and push them straight to broadcast, app, or social.

Cost of inaction

Every live match meant either paying the external vendor again, or manually sourcing and formatting stats under time pressure — neither of which scaled.

Strategy

Build one dashboard on top of Cricinfo's own data: browse modules, customize them, and publish in whatever format the destination needed — closing the vendor dependency at the source.

Core system

Browse, customize, publish anywhere

Who this was for: broadcast producers and digital editors at partner platforms, working against live or near-live matches with little time to spare.

1

Source directly from Cricinfo, not a third-party feed

Every stat module in the dashboard pulled from data Star Sports already had access to, removing the need for a separately licensed vendor.

2

One module, five output formats

API, embeddable iframe, plain text, static image, or social graphic — the same module could serve a TV overlay, an app embed, and a social post without redoing the work per platform.

Trade-off — designing one module to render correctly across five very different surfaces meant the UI had to stay platform-agnostic from the start, not adapted after the fact.
3

Modular, reusable components

Built so future partners beyond Star Sports could be onboarded onto the same system without rebuilding it from scratch.

Sub-tool

Generate Stats — open query vs. guided filters

Who this was for: the same producers and editors, now needing a custom module — a player journey, tournament summary, or match highlight — that didn't already exist as a pre-built option.

Two approaches explored
ApproachHow it workedOutcome
Guided filters Predefined fields — team, tournament, stat type — narrowed the query before the user typed anything Chosen
Open query Free text, chatbot-style — broad results across formats and tournaments, plus related matches, photos, and videos Explored
4

Chose speed and precision over flexibility

Users were almost always working against a live match, with little time to explore or refine an open-ended query. Guided filters got them to the exact stat in fewer steps — which mattered more than the novelty of conversational search.

Trade-off — gave up the flexibility and broader discovery the open-query approach offered, in exchange for reliably fast, precise results under time pressure.

Integration

Getting a dashboard selection on air

Who this was for: broadcast operators, who needed a dashboard selection — match, module, player — to arrive as a ready TV graphic, not just a design mockup.

5

Designed the field-mapping architecture

Defined how each piece of dashboard data — player name, stat value, image — mapped to the corresponding field in the broadcast graphics template, so a dashboard selection could render correctly on air.

6

Built in multi-language handling

The same module could generate in different languages without a separate manual setup per language.
